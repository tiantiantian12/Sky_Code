# LLM Agent 项目 — 核心技术说明（面试向）

> 本文档面向技术面试，梳理本项目的重点功能、实现思路与可展开的回答要点。  
> 项目路径：`D:/qt_project/LLM_Agent`  
> 技术栈：**PySide6 + 自研 ReAct Agent + 多 Provider LLM + Selenium 浏览器接入**

---

## 1. 项目定位

这是一个 **桌面端 LLM 智能体对话系统**，核心能力包括：

- 多模型切换（API 模型 + 浏览器模型）
- **ReAct 推理循环**：模型输出 JSON 工具调用 → 本地执行 → 结果回灌 → 继续推理
- 丰富的本地工具集（文件、网络、数据分析、文档、RAG、工作流）
- 会话记忆、SQLite 持久化、按轮次文件回滚
- Qt 界面：流式输出、Agent 步骤可视化、多任务拆分

入口：`main.py` → `ui/main_window.py`

## 2. 整体架构

```
┌─────────────────────────────────────────────────────────────┐
│  UI 层 (PySide6)                                             │
│  main_window.py — 会话列表、消息气泡、Agent 思考面板、参数面板 │
│  ApiWorker (QThread) — 异步调用，避免阻塞界面                 │
└──────────────────────────┬──────────────────────────────────┘
                           │
┌──────────────────────────▼──────────────────────────────────┐
│  服务层                                                       │
│  ChatService      — 对话/Agent 统一入口、记忆注入              │
│  AgentService     — ReAct 循环、工具解析与执行                 │
│  MemoryService    — 内存上下文（滑动窗口 + 自动摘要）          │
│  StorageService   — SQLite 持久化                            │
│  api_service      — 模型路由（API / 浏览器）                   │
└──────────────────────────┬──────────────────────────────────┘
                           │
         ┌─────────────────┼─────────────────┐
         ▼                 ▼                 ▼
   OpenAI 兼容 API   Selenium 浏览器    本地工具 (~30个)
   (MiMo/DeepSeek…)  (MiniMax/DS/GPT)   file/web/rag/…
```

**设计原则：**

1. **统一门面**：上层只调 `chat_completion` / `AgentService.run_stream`，不关心底层是 HTTP 还是浏览器。
2. **本地执行、远程决策**：浏览器模型只负责「想」和「总结」，工具在本地 Python 执行。
3. **不用 LangChain Agent 解析**：LangChain 仅用于 `@tool` 装饰器；ReAct 循环自研，便于控制 JSON 解析与浏览器特化逻辑。

## 3. 智能体编排（ReAct）

### 3.1 什么是 ReAct？

**ReAct = Reasoning + Acting**：模型在每一步可以：

1. **思考**并输出工具调用 JSON，或
2. 直接给出最终自然语言答案

本项目的循环在 `services/agent_service.py` 的 `_run_iter()` 中实现。

### 3.2 完整执行流程

```
用户输入
    │
    ├─ [可选] split_user_tasks() 多任务拆分（仅 API 模型）
    │
    ▼
ChatService.send_agent_message_stream()
    │  注入 history = MemoryService.get_api_messages()
    ▼
AgentService._run_iter()
    │
    ├─ 组装 messages = [system_prompt] + history + [user_message]
    │
    ├─ 【快速路径】是否命中 preemptive？
    │     条件：浏览器模型 + 意图明确（读/删/扫项目）
    │     或：任意模型 + scan_project
    │     → 本地先执行工具 → 截断结果 → 只发 1 次 LLM 做中文总结 → 结束
    │
    └─ 【标准 ReAct 循环】最多 max_steps 次（默认 10，见 agent_config.json）
           │
           ① chat_completion(messages)  → 调用 LLM
           ② 解析响应中的 JSON 工具调用
           ③ 执行工具 tool.invoke(input)
           ④ 将 assistant 回复 + 工具结果追加到 messages
           ⑤ 若无工具调用 → 输出最终 result；否则回到 ①
```

### 3.3 工具调用格式

模型必须输出（纯 JSON，无 markdown 包裹）：

```json
{"tool": "read_file", "input": {"file_path": "D:/project/main.py"}}
```

单参数工具也支持字符串形式：

```json
{"tool": "read_file", "input": "D:/project/main.py"}
```

系统提示词 `_build_system_prompt()` 会动态注入所有工具的 name、描述、参数 schema。

### 3.4 工具解析（面试亮点）

浏览器模型经常输出畸形 JSON，因此有多层防御：

| 阶段 | 函数 | 作用 |
|------|------|------|
| 修复 | `_repair_malformed_tool_json` | `parameters`→`input`、多余引号等 |
| 多对象扫描 | `_parse_tool_calls` | 从大段文本中 brace-depth 扫描多个 `{}` |
| 容错解析 | `_safe_json_loads` | 转义修复、write_file 多行 content 专用提取 |
| 字段归一 | `_normalize_tool_call` | DeepSeek 的 `path`/`parameters` 映射到标准字段 |
| 意图兜底 | `_build_direct_tool_calls` | 模型未输出 JSON 时，根据用户话术直接构造工具调用 |

**浏览器模型兜底策略更激进**：检测到「无法访问文件」等拒答时，自动在本地执行 read/delete/scan。

### 3.5 浏览器 Agent 快速路径（Preemptive）

文件：`agent_service.py` → `_run_preemptive_browser_tools()`

**动机**：浏览器每轮 ReAct 都要往网页粘贴大段工具格式说明，慢、贵、易 500。

**做法**：

1. 根据用户意图在本地直接跑工具（如 `scan_project`）
2. 删除/写入成功则可直接返回，不必再问 LLM
3. 否则将工具结果截断（约 48KB）后，**只发一条**消息让模型用中文总结

### 3.6 多任务拆分

`split_user_tasks()`（`agent_service.py`）：

1. **启发式**：编号列表、分号、多个动词句等，累计 ≥2 个标记才继续
2. **LLM 拆分**：调用一次模型，要求输出 JSON 数组 `["任务1", "任务2"]`
3. **浏览器模型禁用拆分**（避免额外浏览器往返）
4. UI 用 `TaskPlanWidget` 展示计划，子任务串行执行，每条间隔 500ms

### 3.7 Agent 事件与 UI 映射

`AgentService.run_stream()` 产出事件，`ApiWorker` 转为 Qt 信号：

| 事件 type | UI 表现 |
|-----------|---------|
| `thinking` | 展开「思考中」面板 |
| `thought` | 显示推理文字 |
| `step` | 显示工具名、输入、输出摘要 |
| `code_event` | 语法检查 / 执行结果 widget |
| `result` | 最终回复 + 折叠思考面板 |
| `error` | 错误提示 |

## 4. 工具生态

注册入口：`services/tools/__init__.py` → `get_all_tools()`

| 类别 | 工具 | 说明 |
|------|------|------|
| 文件 | `read_file`, `write_file`, `delete_file`, `list_directory`, `scan_project`, `deep_read_directory`, `search_files`, `run_command`, `execute_code` | 本地 I/O；write 带 Python 语法检查 |
| 网络 | `http_request`, `fetch_webpage`, `api_call`, `download_file` | HTTP 访问 |
| 数据 | `read_csv`, `read_excel`, `analyze_data`, `create_chart`, `transform_data` | 表格分析 |
| 文档 | `parse_pdf`, `parse_word`, `parse_ppt`, … | Office/PDF |
| 工作流 | `workflow_start`, `execute_sequence`, `execute_parallel`, … | 进程内多步编排 |
| RAG | `search_code`, `get_index_status` | ChromaDB + SentenceTransformers |

### 4.1 项目扫描分层策略（scan_project）

**问题**：整项目 `deep_read_directory` 可达 30 万+ 字符，浏览器 API 会 500。

**策略**（`file_tools.scan_project`）：

```
scan_project（目录树 + AST 符号摘要 + 关键小文件全文）
        ↓ 需要改代码 / 看实现细节
read_file（单文件完整内容）
        ↓ 超大仓库
search_code（RAG 语义检索，需先建索引）
```

- Python 文件：AST 提取 import / class / def
- JSON：列出 keys
- 其他：前几行摘要
- README、main.py、requirements.txt 等小文件：全文

Agent 系统提示已规定：**整体分析用 scan_project，改代码用 read_file**。

### 4.2 代码质量闭环

系统提示强制：

1. `write_file` 写 `.py` → 自动 AST + `py_compile` 检查
2. 可执行脚本 → 必须 `execute_code` 验证
3. 失败则修正后重写，直到通过

## 5. 记忆系统

### 5.1 双层存储

| 层 | 模块 | 作用 |
|----|------|------|
| 内存 | `MemoryService` / `SessionMemory` | 供给 LLM 的上下文（有窗口限制） |
| 磁盘 | `StorageService` + `data/sessions.db` | UI 完整历史、元数据、Provider 映射 |

**不是同一份数据**：SQLite 存全量；内存只保留最近 **20 轮**（40 条消息）。

### 5.2 SessionMemory 机制

文件：`services/memory_service.py`

```python
DEFAULT_CONTEXT_LIMIT = 128_000   # token 上限（估算）
SUMMARIZE_THRESHOLD = 0.80        # 使用率超 80% 触发摘要
k = 20                            # 滑动窗口轮数
```

核心方法：

- `add_user_message` / `add_ai_message` — 追加并 `_trim_messages()`
- `get_api_messages()` — 转为 `[{role, content}, ...]` 注入 LLM
- `needs_summarize()` — token 使用率 ≥ 80%
- `get_summarize_messages()` — 取除最近 4 轮外的历史
- `replace_with_summary(summary)` — 旧对话压缩为一条「摘要」assistant 消息

### 5.3 自动摘要流程

`ChatService._auto_summarize()`：

1. 检测到 `memory.needs_summarize()`
2. 另起一次 LLM 调用，把旧消息总结成短文
3. `replace_with_summary()` 替换内存中的旧历史
4. **SQLite 仍保留完整原文**（重启后从 DB 重建内存，再被窗口裁剪）

### 5.4 Agent 模式的记忆范围

**持久化到记忆/DB 的**：用户问题 + Agent **最终**回答。

**不持久化的**：ReAct 中间步骤（工具调用、工具返回）。这些只在当次 `_run_iter` 的 `messages` 列表中存在。

面试可答：这是 **短期工作记忆 vs 长期对话记忆** 的分离——减少 DB 膨胀，但单轮复杂任务仍靠 ReAct 内部 messages 串联。

### 5.5 历史注入方式

**Chat 模式**（`send_message_stream`）：

```
[system] + memory.get_api_messages() + [当前 user]
```

**Agent 模式**（`_run_iter`）：

```
[agent system_prompt 含工具说明] + memory.get_api_messages() + [当前 user]
```

ReAct 循环中继续 append assistant / tool-result user 消息。

## 6. 会话持久化与 Provider 映射

### 6.1 SQLite 表结构（`storage_service.py`）

| 表 | 用途 |
|----|------|
| `sessions` | 会话 id、标题、关联项目路径、时间戳 |
| `messages` | 每条 user/assistant 消息、`turn_id`（回滚用） |
| `file_operations` | Agent 文件操作审计 |
| `provider_sessions` | App 会话 ↔ 浏览器侧会话 |

### 6.2 Provider 会话桥接

App 内 `session_1` 与浏览器里的对话不是同一个 ID，通过 `provider_sessions` 映射：

| Provider | external_id 存什么 |
|----------|-------------------|
| MiniMax | archon API 的 `session_id`（UUID） |
| DeepSeek | 对话页 URL（`/a/chat/...`） |
| ChatGPT | 对话页 URL（`/c/...`） |

流程：每次 `chat_completion(..., app_session_id=session_id)` 传入 App 会话 ID → 各 browser service 查表 / 创建 / 持久化外部 ID。

**面试点**：浏览器模型发消息时，`browser_prompt.compose_browser_prompt()` **只取最后一条 user 内容**发到网页，不会把完整 history 粘贴进输入框；多轮连贯性主要靠 **浏览器侧会话** + App 内存 history（API 模型则发完整 messages 数组）。

## 7. 多模型接入

### 7.1 配置

`config/custom_models.json`：

```json
{
  "default_model": "mimo-v2.5-pro",
  "models": {
    "minimax/agent": {
      "provider": "minimax",
      "model_id": "MiniMax-M3",
      "base_url": "https://agent.minimaxi.com",
      "use_browser": true
    }
  }
}
```

### 7.2 路由（`api_service.py`）

```
find_model_by_display(显示名)
    │
    ├─ provider == deepseek  → deepseek_service（Selenium DOM）
    ├─ provider == chatgpt   → chatgpt_service（CDP 附着 Chrome）
    ├─ provider == minimax   → minimax_service（Selenium + 页面内 axios）
    └─ 其他                  → POST {base_url}/chat/completions
```

### 7.3 三种浏览器接入对比

| | MiniMax | DeepSeek | ChatGPT |
|---|---------|----------|---------|
| 方式 | 独立 Chrome profile，hook `window.__axios` | textarea 注入 + DOM 轮询 | 附着 debug port 9222 的 Chrome |
| 会话 | API session_id | 对话 URL | 对话 URL |
| 流式 | 解析 SSE 文本 | 等 DOM 稳定 | 等 DOM + markdown 提取 |

### 7.4 流式输出

- **API 模型**：真 SSE，`chat_completion_stream` 逐 chunk 解析 `data: {...}`
- **浏览器模型**：先拿全文，再**逐字 yield** 给 UI，保证界面体验一致

## 8. 工作流编排（二级编排）

ReAct 是 **LLM 逐步决策**；`workflow_tools.py` 是 **LLM 可选调用的批处理编排**：

- `WorkflowContext`：进程内变量表
- `execute_sequence`：顺序执行多个工具
- `execute_parallel`：并行（线程池）
- `execute_conditional` / `execute_loop`：条件与循环

支持 `${var}` 占位符替换。适合「一次性规划好多步工具、减少 ReAct 轮数」的场景。

**关系**：ReAct 负责「想下一步」；workflow 负责「按脚本批量跑工具」——两者互补，不是替代关系。

## 9. 文件回滚机制

模块：`services/rollback_service.py` — `RollbackManager`

**粒度**：按 **用户消息轮次**（`turn_id`），不是 Git。

流程：

1. 用户发送消息 → `begin_turn()` → `turn_id++`
2. `write_file` / `delete_file` 执行前 → `record_write` / `record_delete` 快照
3. UI 每条用户消息旁有 ↩ 按钮
4. `rollback(turn_id)`：恢复被改文件、删除本轮新建的文件

**要求**：必须用 `delete_file` 工具删文件，不能用 `run_command del`，否则无法记录快照。

## 12. 常见面试 Q&A

### Q1：你们的 Agent 和 LangChain Agent 有什么区别？

**答**：我们只用 LangChain 的 `@tool` 定义工具，**不用** LangChain 的 AgentExecutor。自研 ReAct 循环直接调 HTTP/浏览器 LLM，自己解析 JSON 工具调用。原因是浏览器模型输出格式不稳定，需要大量定制解析、兜底和快速路径，LangChain 抽象反而碍事。

### Q2：ReAct 循环如何避免死循环？

**答**：`agent_config.json` 里 `max_steps`（默认 10）硬性上限；工具不存在则返回错误字符串；写文件失败会要求模型修正而非无限重试（有语法/执行闭环但受 max_steps 约束）。

### Q3：记忆会不会爆上下文？

**答**：三层控制——① 滑动窗口 20 轮；② token 估算超 80% 自动 LLM 摘要；③ Agent 工具结果在浏览器路径截断到 ~48KB。项目扫描用 `scan_project` 而非全文灌入。

### Q4：浏览器模型怎么「能用工具」的？

**答**：工具不在网页里执行。网页模型只输出 JSON；**本地 Python** 解析并 `invoke` 工具；结果作为下一条 user 消息（或快速路径里一次性总结）再发回模型。`browser_prompt.py` 还会注入「JSON 会由本地程序执行」的说明，减少模型拒答。

### Q5：为什么 MiniMax 用 Selenium 而不是纯 API？

**答**：MiniMax Agent 面向网页，签名与 session 与前端绑定。当前方案用用户 Chrome profile 登录态 + 页面内 axios 调官方接口，绕开签名逆向。代价是依赖本机 Chrome、环境耦合高。`minimax_adapter.py` 是早期 HTTP 逆向尝试，生产路径以 `minimax_service.py` 为准。

### Q6：会话数据存在哪？重启后怎么办？

**答**：`data/sessions.db` SQLite。启动时 `_load_sessions_from_db()` 加载所有会话消息，逐条 `memory.add_*` 重建内存（再被 20 轮窗口裁剪）。Provider 映射也在 DB，浏览器对话可续上。

### Q7：如果让你优化，你会改什么？

**答**（结合现状，显得有思考）：

1. API Key 迁到环境变量，避免进仓库  
2. 文件工具加工作目录沙箱  
3. 引入统一 `logging`  
4. Agent 中间步骤可选持久化（便于调试）  
5. 浏览器模型真流式或统一抽象 Provider 接口  
6. `scan_project` 摘要结果缓存（按目录 mtime 失效）

## 14. 一句话总结（电梯演讲）

> 这是一个 PySide6 桌面 Agent：自研 ReAct 循环驱动 30+ 本地工具，通过统一 API 层同时对接 OpenAI 兼容接口和 Selenium 浏览器模型；记忆采用「SQLite 全量 + 内存滑动窗口 + 自动摘要」，文件操作支持按轮次回滚，大项目用 scan_project 分层扫描控制上下文规模。
